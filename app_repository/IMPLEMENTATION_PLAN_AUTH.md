# app_repository 分布式账号体系与外部会员鉴权重构计划

## 1. 目标概述
重构账号体系，在确保 `app_catalog` 具备**独立运行与一键迁移**能力的前提下，实现主系统（SUNWILL 主站）对外部会员（OEM、客户）的身份管控与行为追踪。

---

## 2. 分布式身份验证架构设计 (Standalone-Ready)

为了支持未来的物理迁移，我们不再依赖 Django 默认的本地 Session 共享，而是采用 **“主系统发号、手册系统镜像”** 的解耦模式。

### 2.1 架构模型：中央身份中心
- **主系统 (Identity Provider)**: 
    - 负责 OEM/客户账号的创建、密码修改、账号禁用。
    - 维护 User 与 OEM/Customer 的物理关系。
- **手册系统 (Identity Consumer)**:
    - 拥有本地 `CatalogMember` 镜像表。
    - 登录动作发生在手册系统，验证过程通过 API 实时请求主系统（或通过 JWT 校验）。

---

## 3. 核心重构步骤

### 第一阶段：主系统账号映射 (Internal Base)
1. **模型改造**: 
    - 在 `OEM` 和 `Customer` 模型中增加 `user` 外键。
    - 增加 `member_token` 字段：一个唯一的随机 UUID，作为该单位的外部通信唯一标识。
2. **Salesperson 升级**: 业务员作为内部用户，保留在主系统 `is_staff=True` 体系内。

### 第二阶段：分布式会员同步逻辑 (The Sync Bridge)
既然物料能同步，账号也要同步。
1. **Webhook 扩展**: 增加 `member_account_sync` 事件。
2. **同步内容**: 当主系统创建客户账号时，Webhook 向手册系统推送：
    - `Username` (加密后的唯一标识或邮箱)
    - `Role` (OEM 还是普通客户)
    - `Authorized_Scenarios` (该客户有权查看的场景范围)
3. **手册端接收**: 在 `app_catalog` 中建立 `MemberMirror` 表，存储这些基础信息以供本地极速鉴权。

### 第三阶段：解耦的身份验证流程
1. **登录方式**: 
    - 用户在手册系统输入账号密码。
    - 手册系统后台通过 API 转发给主系统：“这套账号密码对吗？”
    - 主系统返回 **JWT (JSON Web Token)**。
2. **权限令牌**: 
    - 手册系统在本地 Session 存储该 JWT。
    - 后续所有涉及敏感数据（物性表下载）的操作，手册系统通过 JWT 判断用户身份，无需再次请求主系统。

### 第四阶段：跨系统行为管控
1. **日志聚合**: 
    - 手册系统在本地记录 `VisitorLog` (包含 Member_ID)。
    - 每日定时或通过任务队列将这些行为数据“回流”给主系统。
2. **业务员看板**: 主系统将回流的数据归集到 `app_repository` 的客户详情中，业务员可以看到：“我的客户 A 昨天在独立手册系统中下载了 5 份 PA66 的 TDS”。

---

## 4. 迁移时的配置变更 (Migration Strategy)

| 状态 | 身份验证实现 | 数据库状态 |
| :--- | :--- | :--- |
| **当前 (单体)** | 直接 Django 本地 Auth 校验 | 共享 `auth_user` 表 |
| **迁移后 (解耦)** | 修改手册系统的 Auth 后端为 API 验证 | 物理隔离，通过 API 和 Webhook 通信 |

## 5. 后期扩展：微信/手机号一键登录
通过这种解耦设计，未来可以在主系统接入“企业微信”或“扫码登录”，手册系统无需修改任何代码即可自动获得这些高级登录能力。
