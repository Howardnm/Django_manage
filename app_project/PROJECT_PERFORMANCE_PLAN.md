# 项目成员协作与绩效得分功能规划方案 (修订版)

## 1. 背景与目标
为了客观评价项目团队中各成员的贡献，本项目引入“多成员协作”与“业务导向评分系统”。通过为每个成员设定**工作量占比**，并结合基于项目经营理念的**节点自动评分逻辑**，计算出每位成员在各项目中的加权绩效得分。

---

## 2. 核心模型设计

### 2.1 项目成员模型 (`ProjectMember`)
建立项目与用户之间的多对多关联，管理项目组委会。
- **关联项目** (`project`): 外键指向 `Project`。
- **关联用户** (`user`): 外键指向 `User`。
- **工作量占比** (`workload_share`): 数字类型 (0.00 - 1.00)。
- **成员角色** (`role`): 如“项目主导”、“实验辅助”、“工艺支持”等。

### 2.2 节点评分系统 (`ProjectNode` 扩展)
- **节点得分** (`final_score`): `DecimalField`，默认为 0。该得分由系统根据预设规则自动计算，而非手动录入。

### 2.3 评分规则模型 (`NodeScoreRule`)
定义基于经营理念的评分标准。
- **规则名称**: 如“合格待产”、“已量产”等。
- **对应得分**: 该状态下赋予的分值。
- **触发条件**: 结合 `stage` (阶段)、`status` (状态) 和 `round` (轮次) 的组合。

---

## 3. 业务评分规则逻辑 (核心构思)

系统将根据节点的实际执行情况，对照下表自动判定节点得分：

| 经营状态 (规则) | 对应进度节点/状态 | 判定逻辑 (Trigger) | 规则得分 |
| :--- | :--- | :--- | :--- |
| **开发中** | RND/PILOT/MID_TEST (`DOING`) | 节点处于进行中，且无历史失败记录 | 0 (过程态) |
| **一次送样未反馈** | PILOT/MID_TEST (`DOING`) | 轮次 `round = 1`，且状态为进行中超过 X 天 | 20 (阶段性) |
| **不合格再开发** | RND/PILOT/MID_TEST (`FAILED`) | 节点状态更新为“异常/节点迭代” | 0 (需返工) |
| **多次送样未反馈** | PILOT/MID_TEST (`DOING`) | 轮次 `round > 1`，且状态为进行中 | 10 (进展缓慢) |
| **合格待产** | PILOT/MID_TEST (`DONE`) | 小试或中试节点完成，且未进入下一阶段 | 80 (核心成果) |
| **已中试** | MID_TEST (`DONE`) | 明确完成中试阶段 | 90 (重大进展) |
| **已量产** | MASS_PROD (`DONE`) | 节点进入量产阶段并完成 | 100 (最终成果) |
| **项目终止** | 任何阶段 (`TERMINATED`) | 节点被标记为已终止 | 0 (失败终结) |

---

## 4. 计算逻辑 (Algorithm)

### 4.1 项目总分计算 ($S_{project}$)
项目总分并非简单的节点求和，而是取**当前已达到的最高价值节点的得分**，或者采用已完成节点的加权平均。
建议逻辑：取所有已完成节点 (`DONE`) 中得分最高的那个作为项目阶段性质量分。

### 4.2 成员个人得分计算 ($S_{member}$)
每个成员在特定项目中的最终绩效得分：
$$S_{member} = S_{project} \times Member.workload\_share$$

---

## 5. 开发路线图

1. **第一阶段 (模型构建)**:
    - 创建 `ProjectMember`。
    - 在 `ProjectNode` 中增加 `final_score`。
    - 创建 `NodeScoreRule` 配置表。

2. **第二阶段 (自动评分引擎)**:
    - 编写 `Signal` 或 `Service` 逻辑。
    - 当 `ProjectNode` 保存时，自动检索 `NodeScoreRule` 并更新 `final_score`。

3. **第三阶段 (UI 交互)**:
    - 项目详情页增加“项目成员及占比”配置卡片。
    - 在进度条展示中，同步显示该节点获得的“经营状态得分”。

4. **第四阶段 (统计报表)**:
    - 汇总各成员在不同项目中的得分。
    - 提供年度/季度个人绩效报告导出。
